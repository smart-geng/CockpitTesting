## 2. 现有用例盘点

### 2.1 各文件测的是什么

| 文件 | 条数 | 测的是 |
|---|---|---|
| `bsw/G200Z智能座舱自研项目测试用例-soc底软.xlsx` | 213 | 二级模块全部为“SOC”，即 SoC 底软 |
| `uds/UDS诊断测试用例_V0.2.xlsx` | 652（APP内 356、Boot内 296） | MCU 诊断（APP 与 Bootloader 两种状态），经 CAN 测，不属于 SoC 底软 |

需要注意的几点：

- FM/AM 的 21 条实际在测 MCU。收音芯片挂在 MCU 的 I2C 上（架构图1、§4.2.3）。用例用 `mcu-tool fm tune 103.5` 这类命令直接驱动 MCU，检查 MCU 返回的 `ack=TUNE`。严格说属于 SoC↔MCU 联测。
- 有些用例在 HAL / 服务层，而不在驱动层：GNSS 的 HAL 服务与 AIDL Binder、双系统测试的 eRPC 服务与 message_center、蓝牙 AEC。
- MCU 底软里，UDS 以外的部分都没有用例：MCAL、FreeRTOS、Bootloader 的校验与回滚、功能安全、电源与休眠唤醒。
- Boot 内 UDS 用例没有覆盖刷写下载：没有 36、37 服务，34 只出现 1 次。诊断调查表第 9 页有完整的 CAN 刷写流程（EQC-4185），可以照着补。

### 2.3 对照架构的缺口

以下结论来自检索全部用例的标题、前置条件、步骤和预期。

| 优先级 | 缺口 | 现状 |
|---|---|---|
| P0 | SoC↔MCU 两路 SPI。通道1：GPIO A17 + SPI4 → Linux；通道2：GPIO 1W22 + SPI1 → Android。整车信号都经这两路进仪表和中控 | 提到 SPI 的 13 条都在屏模块下，以断链恢复为主。缺 GPIO 中断、帧完整性、端到端时延、两路数据一致性、MCU 复位后恢复 |
| P0 | MOS 系统级故障隔离。架构 §4.1 写明“任一系统故障不影响对端” | 只有进程级的 kill。缺：Android 内核崩溃或重启时仪表的表现；Linux 崩溃时中控的表现；资源抢占 |
| P0 | 核间通信底层：dts 预留内存、veth0、`192.168.43.100/200:32452/32453`、投屏数据面、IMosCom 接口 | 10 条都在 eRPC / 服务层；投屏只测了控制面 |
| P0 | 启动：u-boot→双系统的启动顺序与分段耗时、A/B 回退 | 只有两条“冷启动亮屏时延”；分区用例只查 A/B 状态 |
| P1 | USB 本身：OTG、U 盘、HUB、热插拔 | 0 条，“USB接口”下全是网络用例 |
| P1 | LVDS 摄像头 ×4（DSer、MIPI CSI0）；AHD 的帧率、时延与多路并发 | 0 条 |
| P1 | 存储可靠性：写入时掉电、eMMC 性能与寿命 | 0 条 |
| P1 | 整机电源：两套系统协同休眠唤醒、唤醒源、异常掉电 | 只有外设级的休眠唤醒；唤醒源只在 3 条仪表屏用例里涉及 |
| P2 | GPU、温度降频、SoC 看门狗与 panic 处理、日志组件（log_manager、linux_monitor） | 基本为 0 |

### 2.4 用例本身的问题（做自动化时会遇到）

- 213 条的“测试方法”全部是“人工测试”。
- 有 10 条引用的附件脚本不在仓库里：双系统测试 4 条、GNSS 2 条、AHD / WIFI / 蓝牙 / 仪表屏各 1 条。
- “USB接口”下 18 条的关联需求 ID 和名称都是占位符“1”。
- 门限没有标出处（例如“屏幕应在 2s 内显示”），需要和需求核对。
- 部分预期无法由机器判定，例如“画面可能异常或无画面，系统不崩溃”。
- 实物名称和架构文档不一致：用例里用的是 `/dev/mcu_spi`，架构 §4.6.3 写的是 `/dev/spidevX.X`。以实物为准。

| 类别 | 内容 |
|---|---|
| 节点与工具 | `/dev/mcu_spi`、`/dev/spi_misc_test`、`spi_test`、`mcu-tool`、`message_ipc_pub` |
| Linux 侧 | systemd 服务 `erpc_channel1`～`erpc_channel3`、`message_center`；日志 `/var/log/message_center.log` |
| Android 侧 | `erpc_service`；取得 root：`adb shell` → `su` → `setenforce 0` |

## 3. 方案一：现有用例的 AI 脚本闭环（当前优先，等硬件）

### 3.1 闭环怎么转

用例 → AI 生成脚本 → 台架执行 → 自动判定并保留证据 → AI 归因。归因分四类：

| 归因 | 处理 |
|---|---|
| 脚本问题 | AI 修改后重跑 |
| 环境问题（设备离线、缺 AP 等） | 标记“阻塞”，不算失败 |
| 疑似产品缺陷 | 带证据起草缺陷单，由人确认 |
| 用例无法判定，或与实物不符 | 记录用例修改建议 |

人只做两件事：评审脚本是否真的测到了用例要测的内容；确认缺陷。

**规则：AI 不得为了让脚本跑通而放宽判定条件。判定条件的任何改动都必须经人工批准。**

### 3.2 可自动化分级

以下是按关键词做的粗分，需要逐条复核：

| 三级模块 | A 纯命令 | B 需物理动作或外部设备 | C 无可执行命令 |
|---|---|---|---|
| AHD摄像头 | 1 | 9 | 0 |
| FM/AM | 10 | 8 | 3 |
| GNSS模块 | 12 | 4 | 0 |
| WIFI | 2 | 19 | 0 |
| 蓝牙 | 7 | 7 | 8 |
| 仪表屏 | 15 | 10 | 0 |
| 中控屏 | 12 | 16 | 1 |
| 音频 | 30 | 4 | 0 |
| 双系统测试 | 7 | 3 | 0 |
| 系统分区 | 6 | 1 | 0 |
| USB接口 | 17 | 1 | 0 |
| **合计** | **119** | **82** | **12** |

**每级怎么做**

| 级别 | 做法 |
|---|---|
| A | 直接做成全自动 |
| B | 先做半自动：需要动手时脚本暂停、提示操作员。以后加继电器板、程控电源、可控 AP，再改成全自动 |
| C | 保留人工 |

**粗分规则**
- 步骤或预期里出现 adb shell、tinymix、modetest、mcu-tool、systemctl、iperf3 等，算作有命令。
- 出现插拔、线缆、触摸、手机、AP、上下电、天线等，算作需要物理动作或外部设备。

### 3.3 框架要点

用 Python + pytest，跑在台架电脑上。

- **设备访问层**：
  - Android 走 adb；
  - Linux 走串口，要处理登录、提示符和超时；
  - MCU 走 `mcu-tool`；
  - 预留程控电源（SCPI）、CAN、继电器的接口。
- **一条用例一个脚本**，脚本里带用例 ID（如 T12590）、所需资源、风险级别。
- **每一步 = 命令 + 判定 + 证据**：
  - 现有用例的步骤和预期大多按 `#` 开头的行一一对应，可以逐行转换。
  - “系统不崩溃”这类说法要拆成可判定的条件：dmesg 里没有 panic / oops、关键进程 PID 没变、uptime 没有归零。
- **结果与证据**：每次运行都记录 Linux、Android、MCU 的版本，保存 dmesg、logcat 和命令输出，并生成汇总表（用例 ID、结果、证据路径）。结果先存在仓库里，以后再考虑回填 APM。

### 3.4 试点

挑 15–20 条 A 级用例：

| 试点组 | 选它的原因 |
|---|---|
| 系统分区 6 条 | 纯查询，最安全 |
| 双系统测试 7 条 | 同时走 Linux 串口和 Android adb |
| FM 命令若干条 | 下发 `mcu-tool` 命令并解析 ack，打通 MCU 这条路径 |
| 仪表屏 DRM 基础若干条 | 解析 `modetest` 的输出 |

衡量指标：
- 脚本首次就跑通的比例；
- 每条脚本平均迭代几轮；
- 能否连续 3 次结果一致；
- 暴露出多少条用例本身的问题；
- 比人工执行节省多少时间。

### 3.5 安全边界

- 先只自动化只读、可恢复的用例。刷机（RKDevTool）、改分区、长时间压力测试暂时不交给 AI 自主执行。
- 台架会话的权限：
  - 查询类命令直接放行；
  - `setenforce`、写 sysfs、`kill`、`reboot` 这类命令，每次都要确认，或者只放行白名单里的。
- 只在 userdebug / eng 版本的台架上运行。

### 3.6 运行方式

- **正常方式**：需要一个能直接访问设备的会话。
  - 在接台架的电脑上 clone 本仓库。
  - 用 Claude 桌面版，或者在仓库目录的终端里运行 `claude remote-control`（会话会出现在 Claude Code app 里）。
  - 会话会自动读取 `CLAUDE.md`，开始前先读本文档。
- **台架没就绪时的替代**：AI 在云端写脚本，人去台架上执行，再把日志推回仓库，由 AI 分析。可行，但每一轮都要有人参与。

## 4. 方案二：补全用例（暂缓）

### 4.1 方法

建“架构对象 × 测试维度”覆盖矩阵，把现有 213 条填进去，空格就是缺口（对照 2.3）。

- **行**：按架构图1 和 §2.1 外设表逐个列出底软对象。
- **列**：用 6 个维度统一作为四级模块的模板：
  1. 驱动加载与枚举
  2. 接口与数据通路功能
  3. 电源管理
  4. 性能
  5. 异常与容错
  6. 并发与长稳

### 4.2 需要的资料

**P0**
- APM 中 SoC 底软相关需求的导出（ID、内容、验收标准）。
- 性能与时间门限：来自《G200产品文档》、《系统需求规格说明书》及其子文档。
- SoC↔MCU SPI 协议：帧格式、校验与序号、GPIO 握手、消息列表与周期、超时与重传。
- 《仪表系统核间通信设计》（文档计划里标为“已完成”）：eRPC 接口、三个通道的分工、message_center 的 topic 与消息格式。
- MOS 资源划分与故障策略：CPU 核、内存、外设各归哪个系统；一侧崩溃时另一侧的期望行为、允许中断多久；看门狗与复位策略。
- 启动流程与 A/B 策略、分区表。

**P1**
- 电源管理设计。
- 原理图《HV9图纸》或硬件接口表；关键器件的型号和手册。
- 两套系统的 dts 与内核配置。
- 版本发布说明。
